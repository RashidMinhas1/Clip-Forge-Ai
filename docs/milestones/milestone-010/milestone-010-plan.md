# MS-010 — Candidate Review UI

## 1. Executive Summary
The MS-010 milestone focuses entirely on providing a user-facing Candidate Review UI to allow users to inspect the short-form clip candidates generated by the AI Clip Discovery engine (MS-009). The UI enables users to view the candidate cards (including scores, titles, hooks, reasoning, excerpts, and timestamps) and approve, reject, or mark candidates for further review. This milestone builds upon the MS-009 contract, consuming existing discovery output, and adds interactive review capabilities to the frontend application without introducing editing or rendering pipelines.

## 4. MS-009 Contract / Dependency Analysis
MS-010 explicitly consumes the following API endpoints and schemas implemented by MS-009:
- **`ClipCandidate` Schema**: Returns `id`, `run_id`, `project_id`, `title`, `hook`, `reason`, `start_time`, `end_time`, `duration`, `score`, `confidence`, `transcript_excerpt`, `status`.
- **API Endpoints**: 
  - `POST /projects/{project_id}/sources/{source_id}/clip-discovery`
  - `GET /projects/{project_id}/sources/{source_id}/clip-discovery/{run_id}`
- **Persistence**: Clip candidates are saved in PostgreSQL via the `ClipCandidate` SQLAlchemy model.
MS-010 uses the existing status field on `ClipCandidate` to handle review state (e.g., `pending`, `approved`, `rejected`) if supported by MS-009, or will require a minimal API update to support state mutation.

## 5. Scope
**AUTHORIZED:**
- Interactive candidate list/grid view.
- Candidate card UI component displaying: title, hook, score, reasoning, timestamps, duration, transcript excerpt.
- Candidate selection and review state mutation (Approve / Reject).
- Empty, loading, and error states for the review workspace.
- Filtering or sorting by score/status if already supported by the backend or feasible client-side.
- Navigation to/Preview of the candidate timestamp in the Source video/audio player (seeking).

## 6. Out of Scope

- Keyframes, overlays, masks, caption styling, caption rendering.
- Final clip generation or rendering pipeline.
- Export pipeline (social-media export).
- Redesigning the existing landing page, project dashboard, or ingestion page.

## 7. UX / User Flow
1. **Entry**: User navigates to the Source page (`/projects/[projectId]/sources/[sourceId]`).
2. **Discovery Loading**: User initiates "Discover Clips" (or views an existing run). The UI displays a loading/polling state.
3. **Candidate Review Workspace**: Once candidates are generated, the UI presents a Candidate List.
4. **Candidate Interaction**: 
   - User clicks a candidate to seek the source media player to the exact `start_time`.
   - User inspects candidate metadata (`title`, `hook`, `reason`, `score`).
5. **Approve / Reject**: User clicks "Approve" or "Reject" on the candidate card. The UI optimistically updates the status and triggers an API call to persist the review state.

## 8. Architecture
- **Service Layer**: The UI acts as a dumb consumer of the MS-009 REST API endpoints.
- **Components**: The Review Workspace is injected into the existing Source Page. It delegates to smaller reusable components (`CandidateList`, `CandidateCard`).
- **Data Flow**: `page.tsx` handles fetching the discovery run. A new API method `updateClipCandidateStatus` might be needed if MS-009 did not provide a mutation endpoint.

## 10. API Contract
- **Existing**: `GET /projects/{project_id}/sources/{source_id}/clip-discovery/{run_id}` (Fetches candidates)
- **API Gap (If MS-009 omitted it)**:
  - **Endpoint**: `PATCH /projects/{project_id}/candidates/{candidate_id}/status`
  - **Request Body**: `{ "status": "approved" | "rejected" }`
  - **Response**: Updated `ClipCandidateResponse`.
  - **Note**: This minimal backend addition is required to persist the review state if MS-009 did not include a PATCH endpoint.

## 11. Database Contract
- **NO DATABASE SCHEMA CHANGES REQUIRED**.
- MS-009 already provides the `ClipCandidate` model. If it includes a `status` field (e.g., `pending`, `approved`, `rejected`), MS-010 will simply update this field.

## 12. State Management
- **UI State**: React `useState` to track the currently selected candidate for media player synchronization.
- **Server State**: Use existing React `useEffect`/polling logic or existing `apiClient` to fetch data. Optimistic UI updates when approving/rejecting to ensure a snappy user experience. No external state management library (like Redux or Zustand) will be introduced.

## 13. Security
- API requests to mutate candidate state MUST enforce Project and Source ownership boundaries on the backend.
- The UI MUST NOT expose or read backend API keys.
- Client-side routing and button visibility must not replace backend authorization checks.
- Sanitized error messages in the UI.

## 14. Testing Strategy
- **Frontend Tests**: 
  - Test candidate card rendering (score, hook, timestamps).
  - Test approve/reject button interactions and optimistic state updates.
  - Test empty/loading/error states.
- **Backend Tests (if PATCH endpoint added)**: 
  - Test `PATCH /candidates/{id}/status` enforces ownership and updates correctly.
- **Regression**: Must run MS-001 through MS-009 backend and frontend tests to ensure no regressions.

## 15. Performance
- **Candidate List**: If the list of candidates is massive, rely on standard mapping. Virtualization is explicitly out-of-scope unless performance actually degrades.
- **Re-renders**: Memoize `CandidateCard` if updating one candidate causes the entire list to re-render.
- **Media Player**: Seeking the media player should not cause the entire page data to refetch.

## 16. Accessibility
- Ensure all interactive elements (Approve/Reject buttons) have semantic `<button>` tags and `aria-label` attributes.
- Ensure the candidate list is navigable via keyboard (`tabIndex`).
- Provide visible focus states for candidate cards.
- Status colors (e.g., green for approved) must be accompanied by text/icons to not rely solely on color.

## 17. Dependencies
- NO NEW DEPENDENCIES REQUIRED. React, Next.js, and standard CSS/Tailwind are sufficient.

## 18. Acceptance Criteria
- **AC-01**: User can view a list of AI-generated clip candidates for a specific source.
- **AC-02**: Candidate cards display exact MS-009 values (score, title, hook, reasoning, timestamps).
- **AC-03**: User can click a candidate to synchronize/seek the source media player to the candidate's start time.
- **AC-04**: User can Approve or Reject a candidate.
- **AC-05**: Review status changes are persisted to the backend API.
- **AC-06**: Unauthorized project candidates cannot be displayed or mutated.
- **AC-07**: No video trimming or editing functionality is exposed.

## 19. Risks & Mitigations
- **Risk**: API gap where MS-009 did not provide a mutation endpoint for candidate status.
  - **Mitigation**: Implement a minimal `PATCH` endpoint tightly scoped to the `status` field.
- **Risk**: Unsynchronized media player state.
  - **Mitigation**: Lift media player ref/time state to the common parent component (`page.tsx`) to allow candidate cards to trigger seek operations.
- **Risk**: Accidental implementation of editing UI.
  - **Mitigation**: Strictly limit UI to Read-Only metadata and Approve/Reject boolean actions.
